## 사용자가 경험하는 흐름

1. 자동 업데이트 플러그인이 포함된 새 APK를 한 번 설치한다. 기존 APK와 앱 ID·서명은 유지하므로 같은 서명으로 빌드한 테스트 APK는 덮어 설치할 수 있다.
2. 앱 시작 및 앱 복귀 시 새 버전을 확인한다. 자동 확인은 15분 간격으로 제한하며, 마이페이지에서 직접 확인할 수도 있다.
3. 새 버전을 검증하고 다운로드하는 동안 현재 앱은 계속 동작한다. 변경되지 않은 파일은 플러그인의 설치 파일/다운로드 캐시를 재사용한다.
4. 다운로드 완료 후 앱 프로세스를 완전히 종료하고 다시 열면 적용된다. 짧게 백그라운드로 보내는 동작으로 진행 중인 게임을 다시 로드하지 않는다.
5. 연결 실패·손상·서명 불일치는 기존 버전을 유지한다. 새 버전이 정상적으로 시작하지 못하면 네이티브 감시 기능이 복구하며, 실패한 버전은 다시 설치하지 않는다.

UI·게임 로직·이미지 등 웹 번들 변경을 배포할 수 있다. Android 권한, 네이티브 플러그인, SDK, 앱 아이콘 및 네이티브 코드 변경에는 새 APK가 필요하다. `native:apk`는 네이티브 구성 지문을 기록하고, `ota:publish`는 구성이 달라졌으면 배포를 거부한다. 네이티브 변경 시 `versionCode`, `versionName`, 업데이트 설정의 `nativeVersion`, 플러그인의 `version`도 함께 올린다.

## 배포 구성

- Supabase Storage의 전용 공개 버킷 `rexrun-app-updates`에는 공개 앱 코드·이미지와 서명된 배포 목록만 저장한다. 건강 정보, 계정, 약 복용 기록은 이 배포 작업으로 전송하지 않는다.
- 파일은 `files/<SHA-256>`에 저장한다. 버전별 목록은 `android/galaxy-test/<nativeVersion>/releases/<webVersion>.json`, 현재 채널은 같은 폴더의 `latest.json`이다.
- 개별 파일은 45 MiB 이하, 전체 번들은 500 MiB 이하로 제한한다. APK 전체를 하나의 Storage 객체로 올리지 않는다.
- 앱에 들어가는 것은 프로젝트 주소와 RSA 공개 키뿐이다. APK에는 Supabase 관리자 키나 배포 개인 키를 넣지 않는다.
- `rexrun-ota-publish` 함수는 RSA 서명과 10분 이내의 요청 시각을 확인한 후, 서명된 파일 목록에 포함된 경로에만 업로드 티켓을 발급한다. 모든 파일의 존재·크기를 확인한 후 채널을 마지막으로 갱신한다. 앱은 배포 서명과 다운로드 파일별 SHA-256을 별도로 검증한다.
- 함수의 `verify_jwt = false`는 이 함수 내부의 서명 인증을 쓰기 위한 설정이다. 서명 검증을 제거한 상태로 배포하지 않는다. 프로젝트에 기존의 광범위한 `storage.objects` 쓰기 정책이 있다면 이 버킷에도 적용되는지 먼저 확인해야 한다.
- Capgo 클라우드 업데이트·통계·채널 주소는 비활성화했다. 앱은 설정된 Supabase 저장소에서만 업데이트를 확인한다.

Supabase Storage와 Edge Functions는 일반적인 SPA HTML 호스팅 서비스가 아니다. 이 구성은 APK의 웹 번들 배포용이다. 브라우저용 데모의 공개 사이트 배포는 별도의 프런트엔드 호스팅이 필요하다.

## 최초 연결

Supabase 조직·프로젝트를 사용자와 확인한다. 새 프로젝트 생성에는 비용 확인을 먼저 진행한다. 기존 프로젝트를 쓰면 기존 데이터와 RLS/Storage 정책을 먼저 확인한다.

`frontend`에서:

```powershell
npm.cmd ci
npm.cmd run ota:init -- --project-url https://<project-ref>.supabase.co
```

`ota:init`은 RSA 개인 키를 최초 1회 생성한다. 기본 위치는 Git에서 제외되는 `frontend/.cache/mobile-updates/publisher-key.pem`이다. 기존 공개 키와 개인 키가 맞지 않거나 기존 개인 키가 없으면 자동 교체하지 않고 중단한다. 재설치/다른 PC 배포를 위해 이 개인 키는 별도로 안전하게 보관한다. `REXRUN_OTA_PRIVATE_KEY_PATH`로 보관 경로를 지정할 수 있다. `VITE_` 환경 변수에 개인 키를 넣지 않는다.

프로젝트 연결 후 저장소 루트에서 Supabase에 로그인하고 함수를 배포한다. CLI를 쓰는 경우 고정 버전을 사용한다.

```powershell
npx.cmd --yes supabase@2.121.0 login
npx.cmd --yes supabase@2.121.0 functions deploy rexrun-ota-publish --project-ref <project-ref> --no-verify-jwt --use-api
```

## 새 웹 버전 배포

변경을 검증한 후 `frontend`에서 APK에 포함된 웹 버전과 기존 원격 버전보다 높은 버전을 지정한다.

```powershell
npm.cmd run lint
npm.cmd run format:check
npm.cmd test
npm.cmd run ota:publish -- --version 1.1.2
npm.cmd run ota:verify
```

명령은 웹 빌드, 파일 해시 계산, 배포 서명, 신규 파일 업로드, 채널 갱신, 원격 채널 재확인을 수행한다. `--prepare-only`를 추가하면 서명된 번들 목록까지만 준비하고 업로드하지 않는다. 앱에서는 다음 시작/확인 때 자동 수신한다. Git 푸시만으로 테스트 채널을 갱신하는 CI는 이 구성에 포함하지 않는다.

`ota:verify`는 현재 채널의 서명과 모든 원격 파일의 크기·SHA-256을 확인한다. `--check-access`를 추가하면 익명 쓰기 차단과 불완전 배포의 채널 변경 차단도 검증한다. 이 추가 검증은 로컬 `.cache/mobile-updates/public-test-key.json`의 공개 키(`{"key":"sb_publishable_..."}`)와 배포 서명 개인 키가 필요하다. 비밀 API 키를 이 파일에 넣지 않는다. 확인 결과는 `.cache/mobile-updates/verification.json`에 저장된다.

실패한 버전의 내용을 고쳐 재배포할 때는 같은 버전을 덮어쓰지 말고 새 버전을 지정한다. 이전 정상 코드로 돌아가야 할 때도 그 코드를 더 높은 웹 버전으로 다시 배포한다. 이미 설치된 앱이 낮은 버전을 다시 받는 동작은 허용하지 않는다.

서명된 308개 경로 / 278개 고유 파일 / 141,357,985바이트의 전체 원격 해시를 확인했다. 신규 업로드는 13개 고유 파일이다. 기존 1.1.0~1.4.0 채널, 공개 APK·설치 QR을 보존했다. CV 브라우저 검사 6개와 공개 HTTPS의 모바일 데모 진입·CV 버튼·실제 모델에 빈 영상 입력·전면 카메라 요청·음성 미요청·카메라 해제·합성 JSON·320/390/430px 화면을 검증했다. 연결된 휴대폰이 없어 실제 기기의 업데이트 수신·실제 동작 정확도는 검증하지 않았다.
