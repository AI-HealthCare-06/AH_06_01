# REXRUN 모바일 앱 뼈대 구상안

작성일 2026년 9월 28일

이 문서는 기획서 v0.2를 화면 구조와 개발 순서로 구체화한 제안이다. 모바일 우선 React PWA를 먼저 완성하고, Android 기기 연동이 필요한 시점에 Capacitor를 추가한다. 첫 시연은 가입부터 첫 퀘스트 완료, 공룡 보상, 기록 확인까지 이어지는 흐름으로 구성한다. 실제 앱 구현이나 도구 설치는 이번 작업에 포함하지 않았다.

## 기획서에서 유지할 기준

- 서비스 이름은 REXRUN으로 통일한다.
- 390px 폭을 기준으로 설계하고 320~430px에서도 입력과 하단 메뉴가 잘리지 않게 한다.
- 하단 탭은 홈, 퀘스트, 대시보드, 상점이다. 마이페이지는 헤더에서 연다.
- 캐릭터 상태는 퀘스트 달성으로 바뀐다. 건강 점수와 캐릭터 상태를 분리한다.
- 매일 퀘스트 3~5개를 제시한다. 체크형은 자기 보고, 기록형은 측정값 저장이 완료 조건이다.
- 공룡 6종, 시들시들·노말·버프 3상태를 자산 구조에 반영한다.
- 능력치는 활동·식생활·수면·기록 4축이며 누적 코인·장비·능력치는 일일 초기화와 분리한다.
- 임상적 효과를 검증한 서비스로 표현하지 않는다. 모든 점수 화면에 기획서의 참고 지표 고지를 둔다.

인증 후 온보딩 미완료 사용자는 마지막 작성 단계로 복귀한다. 온보딩 완료 사용자의 기본 화면은 /home이며, /dashboard는 추이 화면으로만 사용한다. 첫 결과 계산 중에는 대기 상태와 재시도를 제공한다.

건강 프로필은 기획서의 41문항 시드를 조건에 따라 3~6개 화면으로 나누는 구조를 따른다. 실제 전체 문항과 분기 조건은 별도 명세로 확정해야 하며, 기획서의 짧은 필수 입력 목록만으로 나머지 질문을 만들어내지 않는다. 측정 기기가 없거나 최근 수치를 모르는 사용자에게는 미보유·모름 선택지를 제공하는 방향을 제안한다.

## 홈 화면 배치

1. 헤더: REXRUN, 코인, 마이페이지.
2. 오늘 요약: 날짜와 완료한 퀘스트 수.
3. 공룡과 모험: 현재 상태, 한 줄 메시지, 스테이지 진행률. 화면의 시각적 중심이다.
4. 오늘의 퀘스트: 체크형은 홈에서 바로 완료, 기록형은 입력 화면으로 이동.
5. 최근 건강 기록: 측정일과 값, 데이터가 없으면 기록 시작 안내. 자세한 지표는 대시보드로 이동.
6. 하단 메뉴: 홈·퀘스트·대시보드·상점. 실제 앱에서는 안전 영역과 키보드 높이를 고려한다.

기획서의 종이색 #F3E7C8, 먹색 #20211D, 숲색 #397A4B, 머스터드 #E4AE39, 빨강 #D94B3D를 기본으로 한다. 픽셀 스타일은 제목과 캐릭터에 집중하고, 본문과 입력값은 읽기 쉬운 고딕체를 사용한다. 버튼은 약 44px 이상의 터치 영역을 확보하고 색과 텍스트를 함께 사용한다.

## 완료와 보상 흐름

체크형은 완료 요청 → 서버 저장 → 캐릭터·코인·진행률 갱신 → 보상 안내 순서로 처리한다. 기록형은 측정값 검증과 저장이 성공한 뒤 같은 흐름으로 이어진다. 저장 실패 시 완료로 확정하지 않는다.

완료 요청과 코인 지급에는 중복 방지를 둔다. 하루 전체 완료 보너스는 일일 기본 보상의 50%를 한 번 추가 지급하는 방식으로 구현하면 기획서의 총합 ×1.5를 명확하게 관리할 수 있다. 서버 트랜잭션으로 완료 기록과 보상 원장을 함께 저장한다.

퀘스트 완료 시 즉시 바뀌는 것은 게임 보상과 생활습관 기록이다. 건강 지표는 기획서의 일별 재계산 결과가 도착했을 때 바꾸며, 체크 한 번으로 질병 위험이 즉시 줄었다고 표시하지 않는다. 분석 기준일과 최근 측정일을 항상 구분한다.

기록형 입력 오류, 이미 완료한 퀘스트, 네트워크 실패, 결과 계산 중, 기록 없음, 측정값 만료, 추천 생성 실패, 알림 권한 거부, 코인 부족 상태를 화면 설계에 포함한다. 첫 사용자의 빈 추이 그래프는 가짜 데이터로 채우지 않는다.

## 프론트엔드 구조 제안

기획서 스택인 React, TypeScript, Vite, Tailwind, shadcn/ui, Zustand, TanStack Query, Zod, Recharts를 유지한다. 경로 전환에는 React Router를 추가하는 구성을 제안한다.

```text
frontend/
  public/
    icons/
    dinosaurs/       공룡 종류별 3상태 자산
    backgrounds/
  src/
    app/             라우터, 인증 보호, 공통 Provider
    layouts/         MobileShell, Header, BottomNavigation
    pages/           경로별 화면 조합
    features/
      auth/
      onboarding/
      quests/
      records/
      character/
      dashboard/
      shop/
      settings/
    components/      공통 버튼, 입력, 로딩·오류·빈 상태
    services/        API 클라이언트, 결과 이벤트 연결
    schemas/         Zod 입력 및 응답 검증
    stores/          작성 중인 온보딩, 화면 선택 등 UI 상태
    mocks/           가상 사용자, 퀘스트, 분석 응답
    styles/          색·글꼴·간격 토큰
```

서버의 퀘스트·잔액·건강 지표는 TanStack Query로 관리한다. Zustand에는 작성 중인 단계나 선택한 탭처럼 UI에 필요한 상태만 둔다. 코인과 건강 지표를 서로 다른 저장소에서 별도로 계산하지 않는다. API 키는 기획서대로 snake_case로 유지한다.

공통 컴포넌트 후보는 DinoScene, AdventureProgress, QuestCard, MeasurementForm, RewardNotice, HealthMetricCard, TrendChart, EmptyState다. 측정 단위와 수집 시각은 값과 함께 다룬다.

## 백엔드 연결

기획서대로 React PWA → FastAPI → PostgreSQL을 기본 경로로 두고, 오래 걸리는 분석은 Redis Streams → AI Worker로 분리한다. 분석 접수 시 202와 작업 ID를 반환하고 결과는 SSE로 전달하는 구조를 따른다. 이벤트 연결이 끊기면 작업 상태 재조회로 회복할 수 있게 제안한다.

핵심 데이터 묶음은 사용자·건강 프로필, 측정 기록, 날짜별 퀘스트·완료 내역, 캐릭터 누적 능력치, 코인 거래 원장, 보유 아이템, 일별 분석 스냅샷이다. 대시보드는 저장된 스냅샷을 읽는다. 기획서에 없는 세부 API 경로·응답 필드는 후속 API 명세에서 확정한다.

서비스 워커의 첫 범위는 앱 화면 자산 캐시와 오프라인 안내로 제한하는 것을 제안한다. 건강정보 API 응답과 토큰을 무분별하게 영구 캐시하지 않는다. 오프라인 완료와 보상 정산은 동기화 규칙을 확정한 후 추가한다.

| 순서 | 결과물 | 완료 기준 |

| 1 | 모바일 공통 레이아웃과 4개 탭 | 320·390·430px에서 메뉴와 입력이 잘리지 않음 |
| 2 | 가상 데이터 기반 가입·온보딩·홈 | 공룡 선택 후 홈에 도착 |
| 3 | 체크형·기록형 퀘스트와 보상 | 기록 저장, 상태 변경, 중복 지급 방지 |
| 4 | 실제 API·분석 결과·대시보드 연결 | 진행·성공·실패·빈 상태와 재접속 처리 |

이 순서는 개발 착수 순서이며 기획서에서 확정한 기능을 삭제한다는 의미가 아니다. 식단 이미지 분석과 추가 질환은 기획서의 P2 판단 시점에 별도로 평가한다. 첫 시연 목표는 가입 → 공룡 선택 → 퀘스트 완료 → 보상 확인 → 기록 추이 확인이다.

## 데스크톱 모바일 테스트

| 환경 | 적합한 검증 | 남는 확인 |
| --- | --- | --- |
| Chrome DevTools 기기 모드 | 390×844 화면, 터치 이벤트, 반응형, 느린 네트워크 | 실제 Android·iOS 실행 환경과 동일하지 않음 |
| Android Emulator | Android Chrome의 PWA, Capacitor 앱, 권한·뒤로 가기·WebView | 실제 센서, 제조사별 동작, 건강앱 데이터 유입 |
| Android 실기기 | PWA 설치, 터치·키보드, 푸시, 건강 데이터 연동 | 지원할 기기·OS 조합별 확인 |
| Mac의 iOS Simulator 및 iPhone | iOS 앱과 Safari, 플랫폼별 레이아웃 | Windows에서는 Apple의 iOS Simulator를 로컬 실행할 수 없음 |

화면을 만든 후 로컬 개발 서버를 실행하고 Chrome에서 F12 → 기기 도구 모음 → Responsive → 390×844로 확인한다. 작은 320px 폭과 큰 글자 설정도 함께 본다. 브라우저의 iPhone 화면 프리셋은 실제 iOS Safari 검증을 대신하지 못한다.

Android Studio에서는 Device Manager에서 가상 기기를 만들고 시스템 이미지를 지정한다. 기존 SDK를 사용할 때 설치된 플랫폼 패키지와 시스템 이미지는 별개이므로 각각 확인한다. PWA는 가상 기기의 Chrome으로 열고, Capacitor 앱은 빌드한 Android 프로젝트를 실행한다.

Health Connect는 Android SDK와 권한 처리가 필요하므로 순수 PWA에서 직접 읽는 기능으로 설계하지 않는다. Capacitor의 네이티브 연동 계층을 따로 둔다. 테스트 데이터는 Health Connect Toolbox로 주입할 수 있지만, 삼성 헬스 등 실제 데이터 제공 앱과의 연결은 실기기에서 검증한다.

## 필요한 개발 도구와 현재 확인 상태

2026년 9월 28일 이 PC에서 수행한 제한된 읽기 전용 확인 결과다. 경로 존재 확인은 정상 실행이나 전체 개발 환경 준비 완료를 보장하지 않는다.

현재 Node 버전은 조회한 Vite 요구인 20.19+ 또는 22.12+를 충족한다. Android Studio와 에뮬레이터를 함께 사용할 때 공식 Windows 최소 메모리는 16GB, 권장은 32GB이며 CPU 가상화가 필요하다. 이 PC의 RAM과 가상화 상태는 시스템 조회 권한 제한으로 확인하지 못했다. 도구 설치나 시스템 설정 변경은 수행하지 않았다.

## 구현 전에 맞춰야 할 기획 항목

1. **점수 방향과 이름:** 7장의 S 수식은 값이 커질수록 주의가 필요한 형태다. 이를 높은 점수가 좋은 것처럼 읽히는 ‘건강 점수’로 표시하면 혼동된다. 원지표를 유지하고 명칭을 바꾸거나, 검증한 변환식을 별도로 정해야 한다. S는 0~100 밖도 가능하므로 임의로 100−S를 쓰거나 100점 만점 게이지로 고정하지 않는다.
2. **계산과 문구:** 예시 0.7×50+0.3×38은 46.4다. 반올림 규칙을 정하고 ‘고혈압까지 46점’ 같은 거리 표현은 제거하는 방향을 제안한다. 점수 분해 표시도 가중치와 맞아야 한다. 예를 들어 가중 기여도는 35와 11.4다.
3. **대상 범위:** 3장은 10~40대를 주 타겟으로 제시하지만 55세 페르소나와 40~60대 인터뷰 검증도 남아 있다. 초기 시연 대상과 예방·관리 모드 지원 범위를 통일한다.
4. **일일 경계:** 자정 상태 확정과 06시 퀘스트 생성 사이 6시간의 화면·완료 가능 여부를 정해야 한다. Asia/Seoul 기준과 퀘스트 날짜 키를 서버 기준으로 통일하는 것을 제안한다.
5. **온보딩 입력:** 간단한 필수 입력 목록과 41문항 조건부 설계를 하나의 질문 명세로 합친다. 측정값 없음·기기 없음 분기를 명확히 한다.
6. **확장 명세:** 기획서가 참조하는 12장 Capacitor 모듈은 제공 파일 본문의 1~9장에 포함되지 않는다. Health Connect 연동은 추가 기술 검증 항목으로 남긴다.
7. **what-if 표시:** ‘목표까지 n일’은 기획서에서도 타당성 확인 대상이다. 뼈대 단계에서는 충분한 기록과 검증 기준이 없으면 표시하지 않는다.
